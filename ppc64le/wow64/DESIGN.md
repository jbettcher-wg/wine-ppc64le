# 32-bit (i386) guests on the ppc64le port: real WoW64, emulated CPU

The port runs x86-64 Windows programs by making AMD64 a *guest machine*: the
main image is a guest PE, its imports bind to thunk PEs generated by
`tools/spec2thunk`, and every thunk traps into the embedded emulator's callback
which marshals MS-x64 → ELFv2 and calls the native implementation.  README.md
says plainly that this lane does not go through WoW64, and why: WoW64 is
32-on-64 by construction, and an AMD64 guest is not 32-bit.

An i386 guest *is* 32-bit by construction.  This document says which of the
three plausible shapes the 32-bit lane takes, and why; then it walks the
pointer-width, calling-convention, emulator, and TEB questions one at a time;
then it names what is deliberately not done, with the technical reason for
each.  The shape decision drives everything else, so it comes first.

## The decision: real Wine WoW64 (shape a), and why the thunk lane (shape b) is wrong for 32-bit

Three shapes were on the table:

  (a) real Wine WoW64: `dlls/wow64` + `dlls/wow64win` built as native ppc64
      modules, a full set of genuine i386 PE DLLs cross-compiled by clang,
      and a new CPU backend that drives the embedded emulator in 32-bit mode;
  (b) a second guest-machine lane symmetrical to AMD64: i386 thunk PEs in
      `C:\windows\syswow64\`, generated by `spec2thunk` for the i386 ABI,
      each API call marshalled i386 → ELFv2 directly;
  (c) a hybrid.

The port chose (a).  The reasons are mechanical, not aesthetic:

**1. The AMD64 thunk lane works because guest and native struct layouts are
identical.  For i386 they are not, and that difference is the whole problem.**
An AMD64 guest and this port's native PE-side modules are both LLP64: an 8-byte
pointer is an 8-byte pointer, a `WNDCLASSEXW` is the same bytes on both sides,
so a spec2thunk thunk can pass every pointer through untouched and only has to
move *registers* around (MS-x64 positions → ELFv2 order).  An i386 guest's
pointers are 4 bytes, so **every struct that carries a pointer, a handle, a
`SIZE_T` or a `LONG_PTR` has a different layout** — `OBJECT_ATTRIBUTES`,
`UNICODE_STRING`, `OPENFILENAMEW`, `DEVMODEW`, `OVERLAPPED`, `MSG`, every
linked list, every nested pointer graph.  A thunk lane at the Win32 API
surface would need a *deep-copy converter per structure shape*, in both
directions, including graphs the signature alone cannot describe (a struct
holding a pointer to an array whose length lives in another field).
spec2thunk's oracle is clang parsing Wine's headers: it yields signatures, not
conversion semantics.  That converter already exists, complete, debugged and
upstream-maintained — it is `wow64.dll` and `wow64win.dll`, roughly 1500
syscall thunks with exactly those 32↔64 struct conversions
(`OBJECT_ATTRIBUTES32`, `ALPC_PORT_MESSAGE32`, ...), sitting at the syscall
boundary where the surface is narrow and closed.  Shape (b) is a rewrite of
wow64.dll, by generator, spread across every user DLL, without the layout
oracle it needs.  Shape (a) reuses it as-is.

**2. The 32-bit side of WoW64 is real Wine code, so the guest/native boundary
sits where Windows itself put it.**  Under (a), kernel32, user32, msvcrt and
the rest run as genuine i386 code inside the emulator — Wine's own i386 build,
which upstream ships for aarch64 hosts today.  Everything the AMD64 lane had
to fight one API at a time — callbacks registered through struct fields,
`_initterm` walking the caller's initializer table, varargs, x87-returning
CRT functions, apisets, an application's own DLLs — simply never crosses the
boundary: caller and callee are both guest code.  The AMD64 lane's
`thunk_overrides[]` table (dlls/ntdll/signal_ppc64.c) is the measured cost of
putting the boundary at the Win32 surface; (a) pays it nowhere.

**3. The tree already voted.**  configure.ac's own module-list comment (written
when the wow64 group was disabled for ppc64) records the measurement: all of
`wow64win` and 7 of 8 files of `wow64` compile clean for ppc64 as-is; the two
CPU-backend modules are x86-64/arm64ec-specific and need a ppc64 backend, not a
port.  The upstream machinery below them — `load_wow64_ntdll()`,
`init_wow64()`, WOW teb/peb allocation, `user_space_wow_limit`, i386 server
contexts (`context_to_server` has had the I386 pairs all along) — is
arch-generic and already in this tree, because upstream runs exactly this
design on aarch64 with FEX as the CPU.  This port's host arch is different;
the shape is not.

What (a) costs: cross-compiling the i386 PE DLL set with clang (upstream's
`--enable-archs` machinery; op4k has clang/lld/llvm-dlltool), a ppc64 arm for
three asm functions in `wow64/syscall.c`, one new CPU backend, and a small
extension to the emulator bridge.  Each is itemized below.

## Pointer width

**Address space.**  A WoW64 process's 32-bit universe lives below 4 GiB by
upstream construction, and this port inherits it whole:

* `dlls/ntdll/unix/virtual.c` sets `user_space_wow_limit` to 2 GiB, or 4 GiB
  when the main image is `IMAGE_FILE_LARGE_ADDRESS_AWARE`, as soon as
  `is_wow64()` is true — and `is_wow64()` is `!!wow_peb`, set by env.c when
  the main image machine is 32-bit.  Views for the 32-bit side allocate below
  that limit; `NtQuerySystemInformation(SystemEmulationBasicInformation)`
  reports it as `HighestUserAddress`, which is where wow64.dll gets its
  `default_zero_bits = highest_user_address | 0x7fffffff`.
* Every allocation made on behalf of the guest goes through wow64.dll's
  thunks, which pass those `zero_bits` into `NtAllocateVirtualMemory` /
  `NtMapViewOfSection` — so an OUT pointer handed back to the guest is
  representable in 4 bytes *because it was allocated to be*.
* The native side (native ppc64 PE modules, unix libraries, the emulator's
  JIT) lives above 4 GiB — ppc64le Linux maps PIEs and libraries high — and
  its addresses reach the guest only through wow64's converters, which copy
  into guest-visible temporaries (`Wow64AllocateTemp`) or guest-legal
  mappings.  When a native address genuinely cannot be represented (a 64-bit
  mapping address for a 32-bit caller), the wow64 thunk is the place that
  already decides what happens, per syscall, upstream.
* HANDLEs are fine by server construction: wineserver allocates handle values
  as small dense integers, and the wow64 `get_handle`/`put_handle` helpers
  carry the sign-extension rules for pseudo-handles (-1/-2).
* This lane's one *new* low-address obligation is its own: the two bop
  addresses (below) are stored into 32-bit cells (`Wow64Transition`,
  `TEB32.WOW32Reserved`) by wow64.dll via `PtrToUlong`, so the bop page is
  allocated with wow64-style zero_bits and the emulator's cooperative-exit
  page must also be guest-legal (see the bridge section).

**Structure layouts.**  All 32↔64 layout conversion is wow64.dll's and
wow64win.dll's existing job (`OBJECT_ATTRIBUTES32` etc.).  `spec2thunk` learns
nothing at all, because spec2thunk is not in this lane: no i386 thunk PEs
exist, `C:\windows\syswow64\` serves the genuine i386 builds of Wine's DLLs,
exactly as `C:\windows\sysx8664\` serves AMD64 thunks.  The two guest lanes
are different *kinds* of lane and do not share generators.

## Calling convention

Under (a), i386 `stdcall`/`cdecl`/`thiscall`/`fastcall`, callee-vs-caller
stack cleanup, `_Foo@8` decoration, `__int64` in EDX:EAX, structs by hidden
pointer and x87 `st(0)` returns are all **compiler business inside the
guest**: clang targeting `i686-windows` compiles Wine's i386 DLLs, and both
caller and callee of every Win32 API are guest code.  The `.spec` keywords
feed winebuild's i386 backend exactly as they have for twenty years.  None of
it crosses the emulator boundary, and none of it touches the MS-x64
marshaller in signal_ppc64.c.

What *does* cross the boundary is two fixed frames, defined by Wine's own
i386 ntdll stubs and consumed verbatim from upstream's `wow64cpu`:

* **syscall bop** — the i386 ntdll syscall thunk loads EAX with the syscall
  number and `call`s through `Wow64Transition`.  At the trap:
  `[ESP] = return address into the stub`, `[ESP+4] = the stub's caller's
  return address`, `[ESP+8...] = the arguments`, each argument one 32-bit
  stack slot (`args_alignment` is 4 for i386 — wow64.dll's `get_ulong64`
  reassembles 64-bit values from slot pairs).  The backend resumes the guest
  at `[ESP]` with `ESP += 4` and the NTSTATUS in EAX, after calling
  `Wow64SystemServiceEx( EAX, (UINT *)(ESP+8) )`.  The stub's own `ret $n`
  performs the stdcall cleanup — callee-pop stays entirely guest-side.
* **unix-call bop** — `[ESP] = return address`, `[ESP+4] = 8-byte unixlib
  handle`, `[ESP+12] = code`, `[ESP+16] = args (32-bit pointer)`, resume with
  `ESP += 20`.  Dispatched to `__wine_unix_call( handle, code, args )`; the
  handle a 32-bit PE was given already points at that module's
  `__wine_unix_call_wow64_funcs` table (unix/virtual.c hands out the wow64
  table to wow64 callers), so the 32→64 argument conversion happens in each
  unixlib's own `wow64_*` entries, upstream code again.

Two frames, both shapes pinned by upstream; there is no i386→ELFv2 signature
marshalling anywhere in this design.  That absence *is* the design.

## The emulator

**FEXCore decodes and runs 32-bit mode on this backend today.**  Verified by
execution before anything was designed: a static i386 ELF making `int $0x80`
write/exit syscalls runs correctly under the binfmt-registered FEX from the
smc build on op4k (prints, exits with the right code).  Decode mode is
`Config.Is64BitMode`, consumed at Context construction
(`ContextImpl::ContextImpl` clamps `VirtualMemSize` to 1<<32 in 32-bit mode)
and by the tables/dispatcher; segments in 32-bit mode are IR-level —
`OpDispatchBuilder::GetSegment` adds the *cached base* (`fs_cached` et al.)
on prefixed accesses and adds nothing on default DS/ES/SS accesses, so the
flat 32-bit model costs nothing and the ppc64le JIT backend needs no change.

**Can FEXCore host a 32-bit AND a 64-bit guest in ONE process? No, not
without work, and this design deliberately does not need it.**  The evidence
is in the FEXCore sources, not FEX-the-application: `Config.Is64BitMode` is a
`FEX_CONFIG_OPT` read at `ContextImpl` construction
(`Context.h:384`), where `VirtualMemSize`, the Zydis decode mode
(`Core.cpp:916`, `ZYDIS_MACHINE_MODE_LONG_64` vs `LEGACY_32`), the SRA
register count (`Core.cpp:537/562`, 16 XMMs vs 8) and every `LOGMAN_THROW`
entrypoint guard (`Core.cpp:1727`, `AddThunkTrampolineIRHandler`) are baked
in for the life of that Context.  Two modes in one process would mean two
`Context` objects over the *same* guest address space with CPUState migrated
at each mode-switch branch — a FEXCore change, not a bridge one.  This lane
needs none of it: a WoW64 process's 64-bit side is *native ppc64 host code*,
so no x86-64 guest ever coexists with the i386 guest.  One `Context`, fixed
32-bit, is the correct shape — and the bridge enforces it (`process_init32`
and `process_init` are mutually exclusive, second-one-fails).  Heaven's gate
(a 32-bit process far-jumping to CS 0x33) is the one case that would demand
dual mode, and it is out of reach for exactly this reason; see below.

**The trap opcode for 32-bit is `int 0x80` (CD 80).**  `0F 05` SYSCALL is the
64-bit bop and is not decoded as a syscall in 32-bit mode.  In a non-`_WIN32`
FEXCore build, `OpDispatchBuilder::INTOp` routes 32-bit `int 0x80` into
`SyscallOp`, which under `OS_GENERIC` spills the whole register file, stores
RIP = the address *of* the trap instruction, calls the registered
SyscallHandler — the bridge's existing trap sink — and block-ends so a RIP
written by the handler is honoured.  Identical semantics to the 64-bit bop,
same sink, no new trap plumbing.  Two `int 0x80` sites on one low page,
distinguished by RIP — the exact "BopMode" the repo's own `Wow64Probe`
already exercises.

**The run protocol is bounded-run, not trap-callback.**  The AMD64 lane keeps
one `fexbridge_run()` alive and dispatches thunk traps from inside the trap
callback.  The 32-bit lane must not, because of two upstream control flows
that *cut the host stack*:

* `wow64_NtCallbackReturn` ends a user callback with `longjmp` back to
  `Wow64KiUserCallbackDispatcher`'s `setjmp`;
* `wow64_NtContinueEx` ends a user APC by `NtContinueEx` on the 64-bit
  context captured at APC delivery.

On hardware wow64 (and on FEX-as-a-PE on aarch64) everything those jumps cut
is PE frames.  Here, a trap-callback design would have them cut *live*
`fexbridge_run` frames and their kernel-stack syscall frames — an abandoned
JIT run and a dangling syscall-frame chain.  So instead: **`fexbridge_run`
returns to the CPU backend on every trap.**  The backend's simulate loop is
native code; each iteration loads the guest `I386_CONTEXT` into the bridge,
runs until the guest traps or faults, writes the full context back, returns
through the unixcall, and *then* dispatches `Wow64SystemServiceEx` /
`__wine_unix_call` as ordinary PE code on the Win32 stack.  At the moment
either of those upstream jumps fires, no `fexbridge_run` is active and the
kernel stack holds no emulator frames: the jump cuts PE frames only, exactly
as on hardware.  The cost is a full context store/load and one unixcall
round-trip per syscall — the same order of work the AMD64 lane already does
per thunk call (`call_emu_trap_dispatcher` pushes a user-mode callback frame
each trap).  Correct first; turbo later, and `BTCpuTurboThunkControl` is the
upstream-sanctioned place to say "no turbo thunks yet".

**What the bridge must gain (it is the user's sibling repo; extending it is in
scope).  ABI 3 → 4:**

1. `fexbridge_process_init32( uint64_t exit_page )` — like
   `fexbridge_process_init()` but sets `IS64BIT_MODE=0` before context
   creation.  One mode per process is *correct*, not a shortcut: in a WoW64
   process the 64-bit side is native ppc64 — there is no x86-64 guest code in
   the process at all, so nothing ever needs the 64-bit decoder.  (FEXCore
   scopes the mode to the Context; hosting both modes would mean two Contexts
   sharing guest memory, and nothing here needs it.)  `exit_page` is a
   guest-legal executable page of `F4` (hlt) provided by the embedder,
   replacing the bridge's own anonymously-mmapped HLT page: in 32-bit mode
   every guest-visible address must be below 4 GiB (FEXCore's lookup tables
   are sized by `VirtualMemSize`), and the *embedder* owns the low address
   space — Wine's virtual allocator must place this page, not a raw mmap
   racing against Wine's reservations.  The cooperative-exit path routes
   through this page on every trap, so it is load-bearing, not defensive.
2. 32-bit thread setup in `fexbridge_thread_init()` when the process is
   32-bit: Windows-shaped selectors (CS=0x23 flat code with L=0/D=1,
   SS/DS/ES/GS=0x2B flat data, FS=0x53) with matching descriptors in the
   private GDT.  The descriptors matter beyond cosmetics: a guest `pop %fs`
   recomputes the cached base *from the descriptor*
   (`UpdatePrefixFromSegment` reads the GDT qword), so a reload must land on
   the same base.
3. `fexbridge_set_fs_base()` in 32-bit mode also writes the FS descriptor's
   base field, for exactly that reload path.  (`fs_cached` alone carries
   ordinary `fs:` accesses — `GetSegment`'s 32-bit arm reads it directly.)
4. `fexbridge_run_entry()` (the 64-bit one-shot, MS-x64-shaped) refuses in
   32-bit mode with a message instead of building a 64-bit frame.

Nothing else: no RunFrame surgery (bounded-run made it unnecessary), no
context-shape change (the AMD64 CONTEXT carries 32-bit values; the backend
converts to/from `I386_CONTEXT`, including FXSAVE↔FSAVE via the same
`fpux_to_fpu` shape wow64cpu uses), no signal-handler change
(`fexbridge_fault_is_jit`/`fault_unwind` are mode-agnostic and the port's
`emu_handle_fault` serves both lanes unchanged).

**The CPU backend lives in ntdll.**  wow64.dll loads its CPU by name
(`get_cpu_dll_name()`), so the natural upstream shape is a separate DLL — but
this port's emulator plumbing (bridge handle, fault handler, kernel/Win32
stack discipline) is deliberately concentrated in ntdll, whose PE side is an
ELF builtin precisely so it can own such things.  A separate PE module would
need its own unixlib only to reach state ntdll already owns.  So:
`get_cpu_dll_name()` returns `ntdll.dll` for a POWERPC64 native machine,
ntdll exports the `BTCpu*` surface (arch-gated in the .spec), the PE side
implements the simulate loop (`dlls/ntdll/wow64cpu_ppc64.c`), and the unix
side gains three unixcalls beside the AMD64 lane's two: `emu32_init`
(process/bop-page/bridge-mode), `emu32_thread` (bridge thread + FS base;
also thread teardown), `emu32_run` (one bounded run: context in, reason +
context out).  The `WOW64_CPURESERVED` context in the TEB stays the single
source of truth — the loop writes the full guest state there on every trap,
which is what keeps `RtlWow64GetThreadContext`, `BTCpuGetContext`, and the
exception/APC redirections working with zero special cases, and honours
`WOW64_CPURESERVED_FLAG_RESET_STATE` by construction (the loop reloads the
full context every iteration; the flag only decides whether the syscall's
EAX result survives, exactly as in wow64cpu's asm).

`BTCpuProcessInit` sets `WOW64_CPUFLAGS_SOFTWARE` (this is a software CPU:
wow64.dll then creates the cross-process work list and applies the software
breakpoint Eip adjustment).  `BTCpuResetToConsistentState` is a genuine
no-op: a guest fault surfaces as `FEXBRIDGE_RUN_FAULT` *after* the guest
state is already parked in the TEB context, and the backend raises the
exception as ordinary PE code — there is never an inconsistent in-flight
state for it to repair.  The flush/dirty/unmap notifications forward to
`fexbridge_invalidate_code_range` (over-invalidation is always safe; guest
*stores* are caught by the smc build's own detection, these hooks cover
native writes into guest pages — image loads, `WriteProcessMemory`).

**Wine-side arms this lane adds** (each is small; the point is that this is
the *complete* list):

* `server/registry.c`: add `IMAGE_FILE_MACHINE_I386` to
  `supported_machines[]` for ppc64 — the change the existing comment reserved
  for "when there is a 32-bit guest story".  Everything downstream keys off
  the list: `is_machine_supported()`, syswow64 creation, `Wow6432Node`.
* `configure.ac`: `enable_wow64`/`enable_wow64win` gain `ppc64`.
* `dlls/wow64/syscall.c`: ppc64 arms for the three asm functions
  (`raise_exception`, `wow64_syscall`, `cpu_simulate`).  Their `.seh_handler`
  asm cannot be transliterated — this port has no PE unwind format — but it
  does not need to be: on translated-ELF ppc64 the PE side uses Wine's
  frame-chain `__TRY`/`__EXCEPT`, the same mechanism
  `dispatch_user_callback()` already uses here, and each of the three is a
  direct restatement: catch-into-status around a syscall thunk;
  pass-to-guest-and-resume around the simulate loop; capture-raise-redirect
  for `raise_exception` (a volatile flag at the captured context takes the
  place of the patched resume label: a handler that *continues* resumes at
  the capture point with the flag already set and falls through — same
  control flow, no asm).
* `dlls/ntdll/unix/signal_ppc64.c`: `get_wow_context()` returns the cpu-area
  context (one line, the aarch64 shape), and `init_syscall_frame()` gains the
  I386 arm that seeds a new thread's 32-bit context (Eax=entry, Ebx=arg,
  Esp=wow stack, Eip=32-bit `RtlUserThreadStart`, selectors as above, FPU
  control 0x27f / MxCsr 0x1f80 — copied from signal_arm64.c, the reference
  emulated-wow64 host).
* `dlls/ntdll/signal_ppc64.c`: `KiUserExceptionDispatcher` calls
  `pWow64PrepareForException` first, as every other arch's does.
* `dlls/ntdll/unix/loader.c`: the three `emu32_*` unixcalls beside the
  existing emu entries.

## The 32-bit system directory, TEB/PEB

All upstream, verified present in this tree, listed here so the reader knows
none of it is new work:

* `syswow64` the directory and the redirection: `get_machine_wow64_dir()`
  maps I386 → `\??\C:\windows\syswow64\` already; the server creates the
  directory and shares `Software\Classes\Wow6432Node` once I386 is in the
  machine list; `wow64.dll:init_file_redirects()` does system32→syswow64
  filename redirection for the guest.
* The 32-bit TEB/PEB: `virtual_alloc_first_teb()`/`init_teb()` carve the
  `TEB32` at `teb + teb_offset` and set `WowTebOffset` whenever the process
  is wow64; `wow_peb` sits a page after the 64-bit PEB.  The i386 guest
  reaches its TIB through FS — satisfied per thread by
  `fexbridge_set_fs_base( thread, (char *)NtCurrentTeb() + WowTebOffset )`
  in `BTCpuThreadInit`, plus the descriptor write in the bridge so `pop %fs`
  survives.  `NtCurrentTeb32()->WOW32Reserved` is stored by wow64.dll's own
  `thread_init()` from `BTCpuGetBopCode()` — our only obligation is that the
  value fits in 32 bits, i.e. the bop page allocation.
* The 32-bit ntdll: `load_wow64_ntdll()` maps the genuine i386 ntdll PE from
  the build tree (the fork's same-bitness guard specifically lets a genuinely
  32-bit machine through), and `load_ntdll_wow64_functions()` publishes the
  32-bit dispatcher cells that wow64.dll pokes with the two bop addresses.

## What is NOT done, and the technical reason for each

* **Heaven's gate** (a 32-bit process far-jumping to CS 0x33 to execute
  x86-64 bytes — some DRM and anti-cheat does this).  FEXCore's decode mode
  is fixed at Context construction: `Is64BitMode` is baked into the tables,
  the dispatcher and `VirtualMemSize` when the Context is created, and a
  far transfer cannot re-enter the frontend in the other mode.  Supporting
  it means two Contexts over shared guest memory with mid-branch CPUState
  migration — a FEXCore architecture change, not a bridge extension.  A
  guest attempting it gets a legible fault at the far branch rather than
  silent wrong execution.
* **ARMNT (32-bit ARM) guests.**  The machine list gains only I386.  There is
  no ARM emulator in this stack to back `wowarmhw.dll`; adding the machine
  would advertise a lie to `is_machine_supported()`.
* **Old-style WoW64** (`is_old_wow64()`: a 32-bit ntdll.so and a 32-bit unix
  process).  Requires a 32-bit host ABI; ppc64le Linux has no 32-bit
  little-endian ABI to build it against — there is nothing the unix side
  could even be compiled as.
* **Turbo thunks** (`BTCpuTurboThunkControl`): refused with
  `STATUS_NOT_SUPPORTED` exactly as upstream's own wow64cpu refuses them;
  wow64.dll is required to work without them, and does.  The bounded-run
  protocol has an obvious later fast path (dispatch simple syscalls inside
  the trap callback, skipping the unixcall bounce, for syscalls that cannot
  recurse into guest code); it is an optimization with a measured trigger,
  not a correctness item, and it is not in this pass.
* **`CONTEXT_I386_XSTATE` / AVX state in 32-bit contexts.**  The bridge
  context carries x87+SSE (XMM0-7 are what a 32-bit process can name); YMM
  state for 32-bit XSTATE consumers is not marshalled.  The bridge's own
  64-bit lane has the same boundary (its CONTEXT has no YMM home), and
  upstream's `copy_context_64to32` carries a `/* FIXME: xstate */` at the
  identical spot.  A 32-bit app that *requires* AVX via GetThreadContext
  xstate will read zeros; apps that merely *execute* AVX are unaffected
  (FEX executes the instructions; only the context-query surface is
  narrower).
* **Cross-thread `BTCpuThreadTerm` cleanup.**  The bridge's thread state can
  only be destroyed from its own host thread (`fexbridge_thread_term` is
  owner-only by contract).  A thread that exits normally cleans up; a thread
  terminated *by another thread* leaks its bridge state.  Upstream xtajit
  has the same shape (thread cleanup runs on the dying thread's
  `LdrShutdownThread` path); a cross-thread reaper would need bridge-side
  deferred destruction keyed off host-thread death, recorded here as the
  known cost of `NtTerminateThread`-from-outside, which Wine itself calls
  "for shutdown only".
* **A 32-bit `winedbg` story.**  `context_to_server` speaks I386 and a 64-bit
  debugger can read wow64 thread contexts, but no gate here exercises
  debugging a 32-bit inferior; it is untested, not designed-out.

## Status of this pass — implemented and verified

The full lane as designed above is implemented and runs.  What landed:

* **server**: `IMAGE_FILE_MACHINE_I386` added to the ppc64 supported-machines
  list, which is what makes the server accept a PE32 and creates syswow64 /
  Wow6432Node.
* **build**: the i386 PE DLL set builds via `--enable-archs=ppc64,i386`.
  Getting a clean i386 build took four cross-cutting fixes that were latent
  in the fork's single-PE-arch assumptions: `compiler-rt` is now scoped to
  the real PE archs (i386 modules need `__udivdi3`/`__chkstk_ms`); the
  so-builtin disable (ntdll stays ELF) is scoped to TRANSLATED archs so the
  i386 ntdll builds a real PE; `add_import_libs` skips compiler-rt on the
  translated arch's arch-0 ELF link; and `dlls/d3d11,d3d9,d3d12` — the fork's
  DXVK/vkd3d lanes whose marshal tables are 64-bit by construction — get an
  i386 `#else` arm of loud unimplemented-stubs so the whole tree builds.
* **emulator bridge ABI 3 → 4** (`FexBridge.cpp`/`.h`, the user's sibling
  repo): `fexbridge_process_init32(exit_page)`, 32-bit GDT/selector setup in
  `thread_init`, FS-base-writes-the-descriptor in `set_fs_base`,
  `run_entry` refuses in 32-bit mode.  Standalone-proven 14/14 by
  `bridge32_smoke.c` before Wine wiring.
* **wow64/wow64win for ppc64**: the three asm functions
  (`raise_exception`, `wow64_syscall`, `cpu_simulate`) get ppc64 `__TRY`
  arms, plus a `RtlUnwind` link anchor the `-nodefaultlibs` order needs.

### Two defects the bringup found, worth naming

* **The syscall return value must be stored unconditionally.**  The first
  draft gated `wow_ctx->Eax = ret` on `RESET_STATE`, but that flag is set by
  the initial thread-context install and never cleared before the first
  syscall — so the FIRST `NtAllocateVirtualMemory` left the syscall *number*
  in EAX, `RtlCreateHeap` read it as a failing status, `GetProcessHeap()`
  returned NULL, and the guest died in `RtlAllocateHeap` before printing
  anything.  wow64cpu stores `%eax` unconditionally (`movl %eax,0xb0`) and
  sets Eip/Esp *before* the handler; the backend now does the same.  This is
  exactly the class the port's own rule is built around — a wrong value, not
  a crash, invisible to "did it start".
* **`find_builtin_without_file`'s non-bootstrap bail.**  The emulated i386
  ntdll sees i386 as its own native machine, so the bail restricted it to
  installed files and never reached the build tree — but i386 builtins are no
  more staged than the AMD64 guest's.  Gated now on `WowTebOffset`.

### Known-incomplete (each with its reason, none silent)

The "What I will NOT do" section above is the authoritative list — heaven's
gate (FEXCore single-mode), ARMNT guests (no ARM emulator), old-style WoW64
(no 32-bit host ABI on ppc64le), turbo thunks (a measured optimization, not
correctness), 32-bit `CONTEXT_XSTATE`/AVX-in-context (the bridge context has
no YMM home, same boundary as the 64-bit lane and upstream's own
`/* FIXME: xstate */`), cross-thread `BTCpuThreadTerm` cleanup (owner-only
bridge teardown; leaks a terminated-from-outside thread's bridge state), and
a 32-bit `winedbg` story (untested, not designed out).  Nothing else is
stubbed.
